Among the reviewed object detection frameworks, YOLO (You Only Look Once) was studied in detail due to its suitability for real-time robotic systems. YOLO is a single-shot detection algorithm that processes an entire image in one forward pass of the neural network, allowing it to achieve high inference speeds compared to multi-stage detectors. This real-time performance makes it particularly well suited for time-sensitive applications such as search and rescue operations.

YOLO also benefits from the availability of pre-trained models capable of detecting common object classes, including humans. This reduces the need for extensive dataset collection and training, which aligns well with the scope and constraints of the project. In addition, YOLO has undergone continuous development, with successive versions introducing improvements in accuracy, efficiency, and ease of deployment.

Based on the literature review, YOLO was selected for implementation in this project due to its real-time inference capability, its compatibility with Python-based systems, and its flexibility in supporting both general and domain-specific detection models. While the literature emphasizes human and common object detection, the primary deployed use case in this project is fire, smoke, and flame detection to support emergency response scenarios. The dashboard supports selectable YOLO models. The default (primary) model is a clean COCO-trained network (yolov8s.pt) used for general object and human detection — for example person, dog, and cat — and to project detections onto the shared map. A secondary, fire-only model (fire.pt) is available for identifying fire-related hazards in emergency-response scenarios. The fire-tuned model is deliberately kept as the secondary option and is never used as the primary, because its fire fine-tuning degrades its general (COCO) detection performance.

Deploying deep learning–based object detection on mobile robots introduces several practical considerations that directly affect system performance and reliability. One of the primary concerns is computational requirements, as modern object detection models demand significant processing power. This constraint influences model selection and deployment strategy, particularly when operating on resource-limited robotic platforms.

Another important consideration is edge computing, where inference can be performed either onboard the robot or offloaded to a more powerful external computer. Onboard processing reduces dependency on communication links but is limited by available hardware, while offboard processing can offer higher performance at the cost of increased communication dependency. Closely related to this is latency, as detection speed must be sufficient to support real-time decision-making and safe robot operation. Excessive delay can reduce the usefulness of detection results in dynamic environments.

Finally, effective integration of object detection outputs with other system components is essential. Detection results must be properly synchronized with robot control, mapping, and monitoring systems to ensure that perception data can be used meaningfully within the overall robotic framework.

The Robot Operating System (ROS) was a central focus of the literature review, as it forms the backbone of the proposed system’s software architecture. ROS provides a flexible and modular framework for developing robotic applications, enabling seamless integration of sensing, control, perception, and communication components.

ROS is built around a distributed communication model in which nodes exchange data using a publish–subscribe mechanism. This allows sensor data, control commands, and system states to be shared efficiently across different components. In addition, ROS supports service-based communication for synchronous operations and offers an extensive ecosystem of reusable packages. A wide range of development and debugging tools, including visualization and simulation environments, further enhance its suitability for robotic research and development. The strong community support and comprehensive documentation also make ROS particularly well suited for academic projects.

As part of the review, several ROS packages relevant to the project were studied. These include gmapping for SLAM implementation, robot_localization for sensor fusion using the Extended Kalman Filter, the navigation stack for path planning and motion control, tf for managing coordinate transformations, and rviz for three-dimensional visualization. Together, these packages provide a solid foundation for building an integrated robotic system.

Network communication plays a critical role in enabling data exchange between robots and operator interfaces. The literature review examined common wireless communication solutions used in robotic systems, with a focus on WiFi-based communication.

WiFi is widely adopted due to its availability and ease of integration with ROS. The 2.4 GHz band offers longer range but is more susceptible to interference, while the 5 GHz band provides higher bandwidth and reduced interference at the cost of shorter range. Based on these trade-offs and the expected operating environment, 5 GHz WiFi was selected for the project implementation.

The review also considered transport-layer protocols, particularly TCP and UDP. TCP provides reliable data delivery with guaranteed packet ordering, which is advantageous for transmitting critical information such as maps and status updates. Although UDP offers lower latency, its lack of delivery guarantees makes it less suitable for reliable system communication. Building on these considerations, the final implementation adopted ZeroMQ (ZMQ) as the messaging transport layer, using msgpack-serialized envelopes over TCP-based ZMQ sockets. This architecture provides structured publish–subscribe channels for telemetry, map data, and video streaming, alongside a ROUTER–DEALER pattern for acknowledged command delivery with retry and deduplication logic. ROS 2 communication is deliberately confined to each robot’s local network and is not transmitted over WiFi; only the ZMQ gateway protocol crosses the wireless link. For the ESP32-based environmental sensing robot, communication uses HTTP/JSON endpoints for telemetry and control, as this robot does not run ROS.

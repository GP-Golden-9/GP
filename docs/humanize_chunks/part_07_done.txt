The object detection frameworks analysed were YOLO (You Only Look Once), which was studied in detail due to its suitability for real-time robotic systems. YOLO is a single shot detection algorithm which means it processes the entire image in a single forward pass of the neural network, which allows it to achieve high inference speeds compared to multi-stage detectors. This real-time performance makes it especially well suited for time-sensitive applications, such as search and rescue operations.

YOLO also benefits from the availability of pre-trained models that can detect common object classes like humans. This reduces the need for extensive dataset collection and training. This fits well within the scope and constraints of the project. In addition, YOLO has been constantly updated and improved with subsequent versions that increase the accuracy, efficiency and ease of deployment.

Based on the literature review, YOLO was selected for implementation in this project due to its real time inference capability, its compatibility with Python based systems, and its flexibility in supporting both general and domain specific detection models. While human and common object detection is important, the primary deployed use case in this project is fire, smoke and flame detection to facilitate emergency response scenarios. The dashboard allows selecting YOLO models. The default (primary) model is a clean COCO-trained network (yolov8s.pt) for general object and human detection — e.g. person, dog, and cat — and to project detections onto the shared map. A secondary fire-only model (fire.pt) is also available for detecting fire-related hazards in emergency response scenarios. Since the fire fine-tuning degrades the general (COCO) detection performance, the fire-tuned model is never used as the primary one, but kept as a secondary option.

The deployment of deep learning based object detection on mobile robots brings up a number of practical considerations that have a direct influence on the performance and reliability of the system. Computational requirements is one of the major concerns as state of the art object detection models require significant processing power. This limitation influences the model selection and deployment strategy, particularly when running on resource-limited robotic platforms.

Another important aspect is edge computing, where inference could be performed onboard the robot or offloaded into a more powerful external computer. On board processing (OBP) reduces reliance on communication links but is limited by the available hardware, while off board processing (OFP) can offer higher performance at the expense of increased communication dependency. Closely related to this is the latency, as the detection speed has to be sufficient to allow real-time decision making and safe operation of the robot. Too much delay can reduce the usefulness of detection results in dynamic environments.

Finally, efficient integration of object detection outputs with other components of the system is also essential. Detection results have to be properly synchronised with robot control, mapping and monitoring systems, to make sure that perception data can be used meaningfully in the overall robotic framework.

The literature review was focused on the Robot Operating System (ROS) as it is the backbone of the proposed system’s software architecture. ROS provides a flexible, modular framework for building robotic applications that allows for easy integration of sensing, control, perception and communication components.

ROS is built on a distributed communication paradigm, where nodes exchange data through a publish-subscribe mechanism. This allows the different components to exchange sensor data, control commands and system states efficiently. ROS also provides a service based communication mechanism for synchronous communication and a rich ecosystem of reusable packages. It is also suitable for robotic research and development with a wide range of development and debugging tools such as visualisation and simulation environments. Strong community support and comprehensive documentation also make ROS particularly suitable for academic projects.

As part of the review, several ROS packages related to the project were studied. These are gmapping for implementing SLAM, robot_localization for sensor fusion using the Extended Kalman Filter, the navigation stack for path planning and motion control, tf for managing coordinate transformations, and rviz for three-dimensional visualisation. These packages together provide a solid foundation for building an integrated robotic system.

Network communication is a key enabler for data transfer between the robots and operator interfaces. The literature review looked at common wireless communication solutions used in robotic systems, with a focus on WiFi-based communication.

WiFi is a widely used technology due to its easy availability and direct compatibility with ROS. The 2.4 GHz band has a longer range but is more susceptible to interference and the 5 GHz band has higher bandwidth and less interference but shorter range. Considering these trade offs and the expected operating environment, 5 GHz WiFi was selected for the project implementation.

Transport layer protocols, in particular TCP and UDP, were also reviewed. TCP is for reliable delivery of data and it guarantees the order of packets . This is useful for sending important information like maps , status updates , etc . UDP is lower latency but doesn’t guarantee delivery which is not suitable for reliable system communication. With these considerations in mind, the final implementation selected ZeroMQ (ZMQ) as the messaging transport layer, with msgpack-serialized envelopes over TCP-based ZMQ sockets. This architecture offers structured publish-subscribe channels for telemetry, map data, and video streaming, as well as a ROUTER-DEALER pattern for acknowledged command delivery with retry and deduplication logic. ROS 2 communication is intentionally limited to each robot’s local network and not sent over WiFi; only the ZMQ gateway protocol traverses the wireless link. The ESP32-based environmental sensing robot does not run ROS, and telemetry and control communications are done through HTTP/JSON endpoints.

System integration represents the phase in which all previously implemented hardware and software subsystems are combined and validated as a single, coherent autonomous robotic system. In this project, system integration was carried out incrementally during the first four months, following the successful implementation of individual hardware components, software modules, and communication mechanisms.

The objective of this phase was to ensure that sensing, mapping, perception, communication, and monitoring modules operate simultaneously and reliably under real operating conditions. The integration process focused on stability, data consistency, and real-time performance rather than adding new functionalities.

The system integration followed a bottom-up approach, where low-level components were integrated first, followed by higher-level subsystems. This strategy reduced complexity and allowed early detection of integration conflicts.

To ensure supervisor resiliency and automatic recovery, the software stack is managed via systemd services on the Pi robots: gp-robot1.service (Alpha stack), gp-robot2.service (Beta stack), gp-camera.service (isolated video streaming), and gp-discovery.service (localhost FastDDS discovery server). Serial ports are bound to persistent aliases (/dev/rplidar and /dev/mega) using udev rules based on USB vendor and product IDs. A robot-side preflight check script (preflight.sh) gates stack execution by verifying serial connectivity and networking interfaces before launching nodes.

The central Operations Center implements a global A* path planner (dashboard_qt/ui/map/planner.py) running on the laptop. When the operator clicks a target destination, the planner computes a collision-free route over the SLAM occupancy grid, which is inflated by the robot's footprint radius to maintain safe clearances from walls and doorways. If a valid route is found, the MissionExecutor feeds coordinates one waypoint leg at a time to the robot's goto controller, monitoring execution and aborting if progress stalls.

To ensure fail-safe operations, the system integrates a 4-layer command deadman safety chain. Proportional velocity commands are streamed from the PySide6 console at 10 Hz. The robot-side gateway expects a heartbeat every 0.6 seconds, failing which it sends zero velocities to the navigation bridge. The bridge enforces an 0.8-second watchdog before commanding the Arduino serial bridge. Finally, the Arduino Mega firmware implements a flat 1.0-second hardware watchdog that immediately cuts off motor PWM and de-energizes the water pump relay if USB communication is interrupted. Additionally, an end-to-end latched e-stop command ('E') triggers immediate motor shutdown.

The Operations Center projects detected hazards onto the shared occupancy grid in real time. When YOLO detects a fire or smoke label on Beta's video feed, the YoloManager returns the normalized bounding box geometry. Using the camera's horizontal FOV and a pinhole distance estimation model (where distance is inversely proportional to box height), the console calculates the target's relative bearing and range. This target coordinate is transformed into the global SLAM coordinate frame using the robot's aligned pose, plotting a position-smoothed incident marker on the map. The operator is notified via an audible alarm and a pulsing alert banner.

The testing and evaluation phase of the Swarm Emergency Robotics System was conducted to validate the functional and non-functional requirements established during the system analysis phase. The main purpose of this chapter is to evaluate the implemented multi-robot platform under practical operating conditions and to quantify the performance of the most important system modules. The evaluation focuses on simultaneous localization and mapping (SLAM), autonomous navigation support, visual perception, environmental sensing, and distributed communication reliability.

Testing was performed after the completion of hardware assembly, software integration, and dashboard development. Therefore, the reported results reflect the behavior of the integrated prototype rather than isolated theoretical expectations. This approach is important because the performance of a robotic system is strongly affected by the interaction between mechanical motion, sensor noise, network delay, and processing limitations.

The evaluation methodology followed an incremental, bottom-up approach. Subsystems including sensors, mobility controls, communication interfaces, and perception modules were first evaluated in isolation to establish baseline operational metrics. These isolated tests helped confirm that each subsystem produced stable outputs before it was connected to the complete ROS 2 software stack.

After the individual tests were completed, integrated system testing was conducted to assess communication stability, shared spatial awareness, and centralized monitoring performance. This stage examined how the robot behaved when SLAM, odometry, gas sensing, video streaming, object detection, and dashboard visualization were running at the same time. The bottom-up testing sequence reduced integration risk and made it easier to identify the source of errors during the experimental phase.
